Autonomous agents in Agent Lab run with a built-in toolset. It spans content creation, information architecture, diagnostics, research, email dispatch (`sendAgentMail`), internal knowledge (`searchLocalFiles`, `readLocalFile`), and five live HubSpot CRM tools. Agents call these tools directly when a workflow step asks them to draft content, organize files, diagnose runs, check deal stages, sync contacts, or manage the sales pipeline.

Use this page to understand what actions agents can perform and how to connect the CRM tools to your HubSpot account. It also covers what happens when no token is configured and how the refusal gate keeps step results honest.

## Prerequisites

- A HubSpot account with a private app that has CRM object scopes for deals and contacts.
- For the `hubspot_marketing_email` connector: HubSpot Marketing Hub Enterprise, plus the `content`, `marketing.email.read`, and `marketing.email.write` scopes on the same private app.
- A private app access token (personal access token) from HubSpot.
- Access to the environment variables of the server that runs your agents.

## Departmental tool suite

Beyond the CRM tools, the agent runner exposes departmental tools grouped by function:

| Group | Tools | What agents do with them |
| :--- | :--- | :--- |
| Research and ingestion | `scrapeUrlContent`, `extractDocumentMetadata` | Scrape webpage content, headings, and metadata from a URL; extract document structure, authoring metadata, and key entities from raw text. |
| Information architecture | `auditFileInventory`, `proposeFolderHierarchy`, `categorizeDriveFiles` | Scan file storage for counts, duplicates, and sensitive assets; propose folder structures aligned with the seven department playbooks (MKT, SAL, OPS, FIN, FUL, CUL, AFT); map unorganized files into department folders. |
| Diagnostics and delivery | `inspectExecutionLogs`, `verifyReportDelivery`, `checkCompletionCache` | Inspect execution logs and audit traces to diagnose failures; verify reports were stored in the Artifact Vault and dispatched; check completion caches to avoid duplicate runs. |
| Content and creative | `saveContentDraft`, `saveOutputDocument`, `generateVisualSpec` | Save drafted posts, articles, or newsletter copy to the Content Queue and Calendar; save reports, SOPs, and CSV deliverables to the Artifact Vault; generate visual specs and image generation prompts. |

After each step, the queue processor extracts structured artifacts from the agent's output: social posts, calendar items, documents, and visual specs. It scores their quality and persists them to the workspace so deliverables survive the run.

The local knowledge tools respect department unlocks. `searchLocalFiles` and `readLocalFile` only return workflow kit files for departments unlocked in your workspace; a workspace with `ALL` unlocked has no restriction.

## HubSpot CRM tools

The agent runner registers five tools against the HubSpot CRM v3 objects API:

| Tool | Action | Key parameters |
| :--- | :--- | :--- |
| `getHubSpotDeals` | Reads deals with name, stage, amount, pipeline, close date, and create date. | `limit` (default 10), optional `pipeline` filter. |
| `getHubSpotContacts` | Reads contacts with email, name, company, lifecycle stage, phone, and lead source. | `limit` (default 10), optional `searchQuery`. |
| `updateHubSpotDeal` | Updates an existing deal's stage, amount, or name. | `dealId` (required), optional `dealstage`, `amount`, `dealname`. |
| `createHubSpotDeal` | Creates a new deal in a pipeline. | `dealname` and `amount` (required), `dealstage` (default `appointmentscheduled`), `pipeline` (default `default`). |
| `upsertHubSpotContact` | Creates or updates a contact. | `email` (required), optional `firstname`, `lastname`, `company`, `lead_source` (default `AgentLab OS`), `lifecyclestage` (default `lead`). |

Deal stage values follow the standard HubSpot sales pipeline identifiers: `appointmentscheduled`, `qualifiedtobuy`, `presentationscheduled`, `decisionmakerboughtin`, `closedwon`, and `closedlost`.

The agent decides which tool to call based on the workflow step. For example, a step that says "move the Hamarashops deal to closed won" causes the agent to call `getHubSpotDeals` to find the deal ID, then `updateHubSpotDeal` with `dealstage: "closedwon"`.

## Configure the HubSpot token

The agent runner reads the token from the environment at run time. It checks `HUBSPOT_PAT` first, then falls back to `HUBSPOT_ACCESS_TOKEN`:

```bash
# Preferred variable name
HUBSPOT_PAT=pat-na1-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx

# Also accepted
HUBSPOT_ACCESS_TOKEN=pat-na1-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```

When a token is present, every tool call sends a live request to `api.hubapi.com` with the token as a bearer credential. If HubSpot rejects a request, the tool returns the HTTP status code and error body to the agent instead of failing the run. The agent can then report the exact API error in its output.

One behavior is specific to `upsertHubSpotContact`: when HubSpot returns `409 Conflict` because the contact already exists, the tool treats this as a verified existing contact rather than an error.

## HubSpot outbound action connectors

Agents can also draft outbound actions against HubSpot. A draft doesn't reach HubSpot when the agent writes it. Each draft waits in the **Dispatch Decisions** panel of the [Command Center](/platform/command-center). An operator reviews the payload there and clicks **Approve & Send** to release it to HubSpot. Both connectors use the same `HUBSPOT_PAT` or `HUBSPOT_ACCESS_TOKEN` token as the CRM tools.

| Connector | Label | What it does |
| --- | --- | --- |
| `hubspot_contact_upsert` | HubSpot Contact Upsert | Creates or updates a contact, mapping the draft onto the Agent Lab HubSpot property contract. |
| `hubspot_marketing_email` | HubSpot Marketing Email | Creates a marketing email draft in HubSpot Marketing Hub Enterprise from agent-drafted HTML. |

### Contact field mapping

Agents often draft contact payloads with informal keys instead of exact HubSpot property names. `hubspot_contact_upsert` translates these keys onto the HubSpot property contract before it writes the contact:

- Keys that already match a contract property pass through unchanged.
- `engagement_score` maps to `agentlab_intent_level` when its value contains `high`, `medium`, or `low`.
- Any other accepted key without a matching property is kept in the `agentlab_intake_summary` property as `key: value` text. The connector doesn't drop it.

Besides the contract properties, the connector accepts these extra keys: `notes`, `event_id`, `event_name`, `deal_stage`, `deal_value_usd`, `service_line`, `next_steps`, `lead_source`, `profit_engine_link`, and `engagement_score`. Any key outside the contract and this list still fails payload validation.

```json
{
  "email": "jordan@example.com",
  "firstname": "Jordan",
  "engagement_score": "High",
  "event_name": "Founder Summit",
  "next_steps": "Book a discovery call"
}
```

In this example, HubSpot receives `agentlab_intent_level: high`. The event name and next step are saved in `agentlab_intake_summary`.

### Marketing email connector

`hubspot_marketing_email` is the outreach channel for agent-drafted outreach, replacing Instantly. When an operator approves a draft, the connector builds a custom-coded email template from the draft HTML. It then creates a marketing email draft that uses that template in HubSpot Marketing Hub Enterprise. HubSpot handles delivery, open and click tracking, and compliance natively.

| Key | Required | Description |
| --- | --- | --- |
| `name` | Yes | Internal name of the marketing email in HubSpot. |
| `subject` | Yes | Email subject line. |
| `html` | Yes | Email body HTML, used to build the custom-coded template. |
| `from_name` | No | Sender display name. |
| `from_email` | No | Sender email address. |
| `reply_to` | No | Reply-to address. |
| `to_email` | No | Intended recipient, appended to the email name as a label. |
| `event_id` | No | Related event, appended to the email name as a label. |
| `publish` | No | Set to `true` to request a publish through the HubSpot API after the draft is created. |

```json
{
  "name": "Founder Summit follow-up",
  "subject": "Great meeting you at Founder Summit",
  "html": "<p>Hi Jordan,</p><p>Thanks for stopping by our booth.</p>",
  "from_name": "Uncle Robert Consulting",
  "reply_to": "hello@example.com",
  "to_email": "jordan@example.com",
  "event_id": "founder-summit-2026"
}
```

This payload creates an email named `Founder Summit follow-up [jordan@example.com | founder-summit-2026]`.

<Note>
  `to_email` and `event_id` only label the email name so you can see who a draft is for in HubSpot. The connector doesn't send to that address. Attach recipients and scheduling to the email inside HubSpot. If you set `publish: true` and no recipient list is attached, HubSpot refuses the publish and the dispatch reports the error. The draft still stays in HubSpot.
</Note>

## Fallback behavior without a token

If neither `HUBSPOT_PAT` nor `HUBSPOT_ACCESS_TOKEN` is set, the tools do not fail. Each tool returns simulated local data so workflow runs complete end to end in development:

- `getHubSpotDeals` and `getHubSpotContacts` return a small sample pipeline and contact list with a `status` of `simulated_success` and a message noting that no token was found.
- `updateHubSpotDeal`, `createHubSpotDeal`, and `upsertHubSpotContact` return a success payload prefixed with `[Simulated]` describing the write that would have occurred.

<Warning>
  Fallback responses look like successful tool results to the agent. Before relying on agent-reported CRM changes in production, confirm the token is set. Check tool output for `simulated_success` or the `[Simulated]` prefix to tell fallback results apart from live ones.
</Warning>

## Anti-passivity refusal gate

The agent runner classifies every response with a semantic refusal detector before the queue processor marks a workflow step complete. The detector catches two failure patterns:

- **Capability refusals.** The agent claims it cannot act, for example "I do not have direct access" or "unable to access external" systems.
- **Passive non-execution.** The agent acknowledges the task without doing it, for example "I have noted the details" or "I will await further instructions".

When either pattern matches, the queue processor fails the step with an error that quotes the matched phrase as evidence. This gate prevents false-positive completions: a step only counts as done when the agent actually executed the work, not when it produced a plausible-sounding refusal or a polite acknowledgment. Failed steps surface as errors in the run, so you can retry them or inspect the step configuration.

The system prompt reinforces the gate from the other side. It instructs agents to execute immediately, invoke tools to persist deliverables, and never reply with passive acknowledgments or clarifying questions.

## Troubleshooting

- **Agent reports simulated data in production.** No token is set in the environment where the agent runner executes. Set `HUBSPOT_PAT` and restart the server.
- **Tool output shows a 401 error from HubSpot.** The token is invalid or expired. Generate a new private app token in HubSpot and update the environment variable.
- **Tool output shows a 403 error from HubSpot.** The private app lacks the required scopes. Grant read and write scopes for deals and contacts. For the `hubspot_marketing_email` connector, also grant `content`, `marketing.email.read`, and `marketing.email.write`.
- **A step fails with a refusal or passive non-execution error.** The anti-passivity gate caught the agent claiming it could not act or acknowledging the task without executing it. The error quotes the matched phrase. Retry the run; the system prompt instructs agents to always execute with the available tools.
